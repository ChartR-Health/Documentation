An electronic data capture system as an environment in its own right — the software clinical trials actually run on. A model works it the way a study coordinator does: building and amending data dictionaries, entering and correcting records, capturing longitudinal follow-up against the right event, and leaving a clean audit trail.

The environment is a faithful emulator of a widely used research platform's API, built so the workflow can be evaluated without depending on the platform itself.

## What the model works with

A **19-tool** API surface covering the operations a coordinator relies on:

<AccordionGroup>
  <Accordion title="Records" icon="table-list">
    Export, import, and delete records, and generate the next record identifier in a study's sequence.
  </Accordion>

  <Accordion title="Study structure" icon="sitemap">
    Read and amend the data dictionary, list instruments, read arms and events, and read the instrument-event mapping for longitudinal designs.
  </Accordion>

  <Accordion title="Study administration" icon="gear">
    Create a study from scratch, read project information, and list users and data access groups.
  </Accordion>

  <Accordion title="Audit and reporting" icon="file-lines">
    Read the full logging history and run defined reports.
  </Accordion>
</AccordionGroup>

<Note>
  During a graded run the model works entirely through the API. A separate web interface exists for people, but it is not exposed to the model — so a task cannot be solved by reading a rendered page.
</Note>

## Conformance

The API surface is verified against an **unmodified third-party community client** written for the real platform. If a generic client built by someone else can drive our emulator without changes, the contract is right.

That is a stronger guarantee than an internal test suite, because it is not written against our own assumptions.
