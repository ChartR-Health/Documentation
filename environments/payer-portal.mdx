The other side of the revenue cycle. Where [Revenue Cycle Management](/environments/revenue-cycle-management) measures whether a model can drive a payer integration programmatically, this environment is the portal a biller actually sits in front of — the web application where coverage gets checked, authorisations get requested, claims get keyed, and denials get worked.

It is both a human interface and an agent environment. The same workflow can be measured either way, which makes it a direct comparison between how a person does the work and how a model does it.

## Two surfaces, on purpose

A model working a denied claim here gets the biller's tool surface — the typed claim-entry and portal tools a person would use — rather than the three protocol verbs used for first-pass claims in Revenue Cycle Management.

<Note>
  The two environments share an engine and differ in what they expose. That is deliberate: it separates "can a model drive the integration" from "can a model work the queue."
</Note>

### v2.0.0 — Became an agent environment

<Warning>
  This release changed what the environment is. Before it, the portal was a human interface only.
</Warning>

The portal gained three harnesses and a denial task set, exposing the biller's working surface to a model. Work that could previously only be measured by watching a person can now be measured by running a model against it.

### v1.0.0 — Extracted as its own environment

The portal had been a page inside Revenue Cycle Management. This release made it an environment in its own right, with eligibility, prior authorisation, claim entry, remittance, and the denial queue as a coherent working surface, and a caseload that loads when the portal opens.
