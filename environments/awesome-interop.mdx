The same clinical store as [Awesome MCP](/environments/awesome-mcp), reached the way an integration engineer would reach it. There is no tool list. The model gets a shell, a base URL, and a bearer token, and has to construct every call itself.

This environment answers a different question from its twin. Awesome MCP asks whether a model knows what to do clinically. Awesome Interop asks whether it can actually do it against a real interface — finding the right resource, shaping the request, handling the error vocabulary, and working within the access it was granted.

## How the model acts

Shell commands. The environment injects the base URL, a bearer token, the decision-support context, and the message endpoints; everything else is up to the model.

<Note>
  **Scopes are deny-by-default.** A model has to work within the access it was actually granted, which makes authorisation failure a realistic and measurable outcome rather than an edge case.
</Note>

### Clinical decision support

CDS Hooks here is not a passive notification. The model **authors the card response itself** and posts it back; valid suggestions are then accepted and signed by the simulated clinician. A model is being measured on whether it can produce a well-formed, clinically appropriate decision-support response, not on whether it can read one.

## Twinned with Awesome MCP

Every task in this environment has a twin in [Awesome MCP](/environments/awesome-mcp) with **byte-identical grading material**, enforced by a cross-environment equivalence test.

That pairing is the most useful thing about this environment. The same clinical work, graded the same way, across a curated tool surface and a raw protocol surface — so the difference in a model's score is attributable to the surface rather than to the task.
