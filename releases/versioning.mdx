Every ChartR environment carries its own version in the form `vMAJOR.MINOR`.

Versions are per environment, not per platform. [Awesome MCP](/environments/awesome-mcp) v2.2 and [Awesome Interop](/environments/awesome-interop) v1.1 have no relationship to each other beyond a shared clinical store.

## What the two numbers mean

The question a version answers is not "how much changed" but **"can I still compare my results"**.

  </Card>

  <Card title="MINOR" icon="plus" horizontal>
    New capability. Existing work is unaffected.

### A major bump means re-baseline

Something changed about what the model can observe, the actions available to it, the protocol it works through, or the interaction loop.

A score from before a major release cannot be meaningfully compared with one from after it. The environment is asking a different question.

<Warning>
  If you are tracking a model against an environment over time, a major bump is a signal that your baselines are stale. Re-run them.
</Warning>

The clearest example is [Revenue Cycle Management](/environments/revenue-cycle-management) v2.0, where the action space collapsed from roughly forty-five typed tools to three protocol verbs. A model's score on v1.1 tells you nothing useful about its score on v2.0.

There have been **three** major bumps beyond an environment's first release. You can see them marked on the [release timeline](/releases/timeline).

### A minor bump is additive

A new capability, workflow, or supported task category, added without disturbing the existing surface. Work that ran before the release runs the same way after it.

[Awesome MCP](/environments/awesome-mcp) v2.1 added bulk export without changing any existing tool. If you were running chart-level tasks before it, your results still stand.

## What is not in the timeline

The [release timeline](/releases/timeline) records changes to what an environment _is_. It deliberately excludes routine work that does not change the evaluation:

- Bug fixes and reliability corrections
- Dependency and infrastructure changes
- Internal refactors
- Content and data corrections that do not alter intended semantics

<Note>
  These ship continuously and do not receive a version entry. An environment at v1.2 today and v1.2 last week is the same evaluation, but it is not necessarily the same code.
</Note>

A correction can still move measured scores — fixing a defect that was penalising models will raise them without any model getting better. Where a fix is large enough to affect comparability, it is treated as a major bump rather than being folded in quietly.

## Status labels

  <Card title="Live" icon="circle-check" horizontal>
    Available to run today.
  </Card>

  <Card title="In development" icon="circle-half-stroke" horizontal>
    Built and runnable internally, surface still moving. Expect major bumps.
  </Card>

<Note>
  Status is not a difficulty claim. An in-development environment is not easier or harder than a live one — it is less settled.
</Note>
